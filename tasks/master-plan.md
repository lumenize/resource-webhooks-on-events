## Motivation

**MCP clients want an efficient way to keep local copies of resources up to date in near real time.** A webhook delivers each change without the client holding a connection open.

Keeping a copy current needs only the newest value, though, not every event on the way to it, so it calls for a different contract than a stream of events: here, an event only says that something changed, and a catch-up brings the newest value. It also differs from the state sync needs of tasks in other ways.

A client watching a resource today has three problems:

1. **It must hold a stream open or poll.** `notifications/resources/updated` arrives only on a `subscriptions/listen` stream, since [SEP-2575](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2575). A long-lived stream fits load-balanced and edge infrastructure poorly: proxies close idle connections, edge and serverless platforms cap how long a request may run, and a deploy or scale-in drops every stream an instance holds. Since 2026-07-28 a broken stream cannot resume, so a change made while it is down is lost without a trace. Polling trades delay against cost instead: every few seconds spends a request per resource per interval, mostly to learn that nothing changed, and every few minutes leaves the copy minutes stale.
2. **It cannot tell whether it already holds the latest value.** The notification names the URI and nothing else, so a client must read the resource again to find out, even the client that made the change.
3. **Catching up after a disconnect is inefficient.** A client back from a disconnect cannot tell which resources changed while it was away, so it must read every resource it watches again.

### SEP-3415's open question 2

SEP-3415's Open Question 2 sketches a minimal implementation of resource subscription over Events, using "a reserved `mcp.resource.updated` event type whose arguments are `{uri}`". This extension sends that event type. **However, a resource is state, and a watcher cares only about the latest version, not every change.** Three edits while a receiver is down leave it needing only the third. On SEP-3415's thread on 2026-10-16, Peter Alexander (@pja-ant) [wrote](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415#issuecomment-6215654779) that watching state and consuming messages "will need different handling and different APIs". The two "should likely share a bunch of the same machinery", he went on, but whether they should share an API "requires some thought and discussion". Here the event delivered over websockets is the shared machinery, and carries no state, only which resource changed and at which moment. The different API is the catch-up, which brings the newest values.

### Why is this different from task state sync?

**Task state is closer to a resource than to a stream of messages, but it is still different.** Peter put the two on the same side: "this is very much the same thing (observing task state vs stream of messages)". A task's state, though, is a small record the Tasks extension defines, with no media type and no version to patch from, so its newest value can go whole, as `notifications/tasks` already sends it. A resource needs versions and patches. Resources also come in collections, such as a template's members, which a client watches as one and catches up on with one call. So this proposal starts with resources, and tasks could reuse what it builds, as this proposal reuses SEP-3415's events and webhook delivery. Timing played a part too: this work began before the Tasks extension joined this working group on 2026-10-16.

**This extension prototypes what a different API for resource state sync might look like.** It uses SEP-3415's events and webhook delivery to say that a resource changed, and an API of its own for the state.

### Why now?

Two changes to MCP make this the time.

**MCP is getting webhooks.** SEP-3415's webhook delivery is the catalyst for this work. It gives an MCP server a way to reach a client that holds no connection open, and this extension takes it as it stands. Clients already accept these webhooks while SEP-3415 is still a draft. [ChatGPT](https://developers.openai.com/plugins/build/mcp-events) receives Events by webhook on protocol `2026-07-28`, and so do the MCP packages of Vercel's AI SDK, Mastra and TanStack AI, in versions released in October 2026, and OpenClaw's `mcp-events` plugin in its beta builds.

**MCP now serves skills as resources.** [Skills over MCP](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/2640-skills-extension.md), SEP-2640, is Final. It serves each skill's files through `resources/read`, and each of a skill's folders as a resource whose `mimeType` is `inode/directory`. So every host that adopts it reads resources, and a host may use a skill only while its files match the manifest it approved. The group behind it chose resources in part because they have "a subscription model for updates", as its [decision log](https://github.com/modelcontextprotocol/ext-skills/blob/main/docs/decisions.md) records, and since 2026-07-28 that model reaches a host only over an open `subscriptions/listen` stream. Yet nothing tells the host that a file changed: it asks again with `skills/get`, and SEP-2640 "defines no shared version or cache token" by which it could compare what it holds with what the server now has. This extension's moments supply exactly that, for every host that loads skills over MCP.

### Use cases

- **A client behind a gateway.** A client on a laptop or in a browser has no URL a server can reach. In SEP-3415's forward-proxy deployment, it names its gateway's URL instead, and the gateway verifies each delivery and passes it on by whatever channel the two share.
- **A collection of documents.** A client subscribes to `https://notes.example/notes/{id}` and hears about each note created, edited or deleted, then catches up from its moment after a night away.
- **A skill served over MCP.** A host that loaded `skill://code-review/SKILL.md` through Skills over MCP may use the skill only while its files match the manifest it approved. Today it learns of a change only by calling `skills/get` again, when the entry's `ttlMs` runs out. Subscribed to the skill's files, it hears of each changed file as it changes, and can refresh the entry and ask for approval again before the model next uses the skill.

## Differences from the prior experiment

The prior experiment is the Resource Webhooks proposal and its prototype, `resource-webhooks-standalone`.

- **Events are `notify` only.** An event carries none of the resource's contents. This means that recipients need another round trip, unless they already hold the change. It also means that `patch` and `full` forms only come into play for the catch-up. My logic here is a tradeoff of optimum efficiency against a political calculation on greater chances of approval. Approval chances are increased if we use a custom event exactly as proposed in Peter's open question 2 and this flavor has a simpler contract than the prior experiment. Our goal of near real-time is almost completely achieved. And, our goal of efficiency is 50-75% achieved.
- **A lost, repeated or late event does no harm.** It carries no state, so the worst it can do is prompt a catch-up the client didn't need. The prior experiment's deliveries carried state, which took rules about the version each one starts from, and about what a resubscribe drops, to keep a late one from overwriting a newer copy.
- **A single moment serves old/new/version/ETag/revision purposes** because it's ever increasing by string sort order. I think this will be acceptable even to the stateless load-balanced implementors. They must already assume that there is one server per uri-specification, because that's the finest granularity they have for load-balancing today. The soft spot in that argument is that incrementing PKs in DBs are out of style. For folks who can't have one, perhaps ULIDs, minted in one atomic step per timeline, are an acceptible alternative. - **Open: the word "moment".** The Filesystems strawman calls a resource's stamp its `revision`. Here, we require that a resource's revision MUST be its moment, so the two could share one name. We say "moment" because a reader needs the sense that it only ever moves forward in time, which "revision" lacks. The strawman is early enough that we may be able to ask it to say "moment" instead. If we switch to "revision" later, readers will already have the concept. Until this is settled, the strawman's methods and change-set entry keep their field, `revision`, and it holds a moment.
- Moments on a timeline MUST strictly increase when string sorted, so no two changes share one. So, ULIDs, leading-zero-padded strings of fixed length for a DB counter integer, etc. will work. ISO date strings work only at a precision finer than the time between changes: to the second, they can't serve a timeline that changes twice in one second. A change that touches several resources in one atomic step takes one moment for all of them.
- Moments on a timeline MUST become visible in order [That wording "visible" is awkard to me. It opens the question of who is looking. Can you think of a better way to word that?]: once the server has handed out a moment, no change at that moment or an earlier one can appear. This is SEP-3415's "safe watermark", held by a timeline instead of a subscription. A server meets it by checking that each new moment is later than the timeline's current one, and committing the change, in one atomic step. It needs that check however it mints moments. Example: a Cloudflare Durable Object instance per timeline does both by its single-threaded nature. In Postgres, the change's own transaction runs `UPDATE timelines SET moment = $new WHERE id = $timeline AND moment < $new`, and mints again when no row changes. The implementor's trade: one timeline per server serializes every write the server takes, and one per uri-specification serializes only that one's.
- How a server mints moments decides only how often that check rejects one. Example: a ULID minted on a server whose clock runs behind the timeline's current moment is rejected, and the server mints again. A ULID minter in monotonic mode never mints one earlier than its last, even when the clock steps back, so on a timeline with one minter, the check never rejects.
- A resource's moment MUST be its revision in the sense of the Filesystems strawman, so `resources/update` and `resources/delete` check `ifMatch` against that one resource's moment. The prototype implements the strawman's four methods, `resources/stat`, `resources/create`, `resources/update` and `resources/delete`, as a second strawman. The strawman's clients compare revisions for equality only, and ours may also sort them.
- A client keeps the latest moment it has caught up to for each subscription, and each copy's moment.
- When a client's write succeeds, it sets that copy's moment to the one in the reply. Its subscription's moment moves only on a catch-up, since others' changes can land in between. Example: X has caught `tickets/{id}` up to `107`. Y updates ticket-9, at `108`. Then X updates ticket-3 with `ifMatch: "101"`, at `109`. Had X moved its subscription to `109`, it would never fetch ticket-9's change.
- After each change, the server MUST send an `mcp.resource.updated` SEP-3415 event to each subscription covering the resource. Its `data` is the strawman's change-set entry, `{uri, effect, revision}`, where `effect` says what the change did: `created`, `updated` or `deleted`. Example: `{"uri": "tickets/ticket-3", "effect": "updated", "revision": "109"}`. This answers the strawman's open question of whether a notification carries its change-set entry. A deletion's entry also carries its moment, as `revision`, where the strawman's carries only `previousRevision`. SEP-3415's own `cursor` field stays absent, which SEP-3415 reads as null, no replay, since the catch-up does replay's job.
- When a client receives that event, it MUST catch up, unless it already holds that uri, or its tombstone, at that moment or later. The writer does, so it skips its own change with no rule of its own.
- A client SHOULD also catch up after each SEP-3415 refresh, so an event lost past its retries costs at most one refresh interval.
- A catch-up names an existing subscription's uri-specification, the client's moment for it, and the form it wants, `full` or `patch`. It always covers the whole subscription, even when the event that prompted it named one uri inside it, so the subscription's moment can advance. It returns each change since that moment in that form, deletions as tombstones, and the timeline's current moment, all read from one state of the timeline. When the server no longer holds every change since that moment, the result says so and carries the whole current state instead. The rest is the existing prototype's subscribe and resubscribe with catch-up contract.
