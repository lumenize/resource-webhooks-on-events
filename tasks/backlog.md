## After the working group reads the proposal

- [ ] **Build the reference implementation in an official SDK.** An Extensions Track SEP needs one before review. It waits for the working group's feedback on [PR #19](https://github.com/modelcontextprotocol/experimental-ext-triggers-events/pull/19), which may change what it builds. Since 2026-11-11 the proposal has one method, `resources/collection/sync`, and each event carries `previousMoment` (`tasks/sync-method.md`), and the rows below are written for that. The likely home is the Python SDK, on [python-sdk#3822](https://github.com/modelcontextprotocol/python-sdk/pull/3822), which adds SEP-3415's poll and webhook delivery; the TypeScript SDK had no SEP-3415 pull request on 2026-11-06.
  - **A store API of the package's own, shaped like `Timelines` in `src/server-role/version-store.ts`, with an in-memory backend and a SQLite one** (Larry, 2026-11-06). It mints moments that sort (R3), gives one moment to a write that touches several resources (R4), gives a deletion a revision and keeps its tombstone (R7, R21), keeps the history catch-ups and patches read (R13, R19), reads contents with their revision for a first read (R7, R22), answers a timeline's latest moment (R13), and runs a hook once a write commits, which sends the event (R10).
  - **Serve the strawman's write methods through that store**, not through the Filesystems prototype's `ResourceOperations`. At db67f78 it builds each write's result itself, with one entry and no revision for a deletion, so it can't meet R4 and R7.
  - **Stamp each `resources/read` item's revision with a middleware the server author installs.** At a5e0630 an `Extension` can't wrap `resources/read` or add middleware, and an `MCPServer` resource's `meta` is fixed when it is registered. The middleware answers `resources/read` for the store's uris from one store read, so each revision matches its contents. The lasting fix is an SDK hook that lets an extension supply resources, which the strawman's prototype asks of SEP-3371 (its gap 3).
  - **Make the subscription from `resources/collection/sync`, in one step with the read of its result (R18).** A sync that carries a `delivery` runs every check `events/subscribe` runs, then writes the subscription and reads `nextFrom` with nothing between them, and a sync that is refused writes none. Whether #3822 lets another method's handler make a webhook subscription that way was not looked at on 2026-11-11. This prototype does it in `ServerRole`'s `#sync`, over `Events.verify` and `Events.commit`.
  - **Keep one moment for each subscription, and send it as `previousMoment` (R10).** The server stores the moment of the last event it sent a subscription, sets it to the timeline's latest moment whenever the subscription is written, and stores nothing for an event it withholds. Where #3822 could keep a value for each subscription, and whether its `transform` can read and replace one, was not looked at on 2026-11-11. This prototype keeps it in `Subscriptions`, as `lastEventMoment`.
  - **Check access at subscribe time** (R25). A sync is checked as a read, so a sync with a `delivery` needs no check of its own. For `events/subscribe`, at a5e0630 an `on_subscribe` hook that raises `MCPError` refuses the subscription or poll lease. An event's own check is a MAY, which #3822 can't do for an emitted event, since `match` and `transform` get no principal, and which the build can leave out.
  - **Send `cursor: null` on each event (R10's SHOULD).** At a5e0630 an emit-fed type always delivers its buffer's position, and a check function that returns `cursor=None` has its events dropped, since a null cursor reads as "start from now". Until #3822 offers a type that doesn't replay, the build sends the buffer's cursor.
